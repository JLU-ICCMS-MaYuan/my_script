# AGENTS 协作核心规范

## 一、基础语言规范
- 所有与助手的交互必须使用中文，避免歧义。
- 所有文档（含本规范）遵循“层级清晰、分类规整、重点突出”的排版原则。

---

## 二、需求处理核心流程

### 2.1 需求优化
- 用户提需求后，明确边界（做/不做范围）、补充缺失信息（场景/约束）、修正歧义，形成清晰需求描述。

### 2.2 确认与执行
- 向用户同步“优化后需求+执行方案（步骤/工具/预期结果）+待确认疑问”，**获明确确认后启动执行**，严禁擅自操作。

### 2.3 记录更新
- 将“用户问题+助手方案”按“项目模块/需求类型”分类记录至对应目录的 **AGENTS.md**，**禁止线性堆砌**；若涉及新分类，先更新文档大纲再补充记录。

---

## 三、Git 提交规范

### 3.1 提交时机与前置检查
- **提交时机**：完成需求处理后，立即执行提交，确保痕迹可追溯。
- **前置检查**：启动需求处理前，必须执行 `git status`，若存在未提交文件（modified/untracked），立即提醒用户：

当前目录存在未提交文件，列表如下：
<粘贴git status输出内容> 请确认是否先提交再处理本次需求？（回复“先提交”或“暂不提交，继续处理”）


### 3.2 提交操作步骤
1. **暂存文件**：`git add <文件路径>`（指定文件）或 `git add .`（所有待提交文件）。
2. **执行提交**：`git commit -m "[YYYY-MM-DD HH:MM:SS] <需求类型>：<修改内容>"`，三要素缺一不可。示例：`git commit -m "[2025-11-10 16:45:00] 规范优化：精简AGENTS.md，修正日志分类规则"`。

---

## 四、编码与 PR 协作规范

### 4.1 编码基础约束
- **语言**：强制 TypeScript 且启用严格模式 (`strict: true`)。
- **命名规则**：组件用 PascalCase（如 `UserProfile.tsx`），工具函数用 camelCase（如 `formatDate.ts`）。
- **样式与异步**：使用 Tailwind CSS，禁止使用内联样式；所有异步函数必须处理错误（`try/catch` 或 `Promise.catch`）。
- **工具优先级**：功能场景推荐工具排除目录文件名搜索 `fd.git`、`node_modules`、`dist`、`coverage` 文本内容搜索 `rg`（ripgrep）代码结构搜索 `sg`（ast-grep）。

### 4.2 PR 协作规范
- **分支命名**：前缀+描述，前缀可选 `feature/`（新功能）、`fix/`（修复）、`refactor/`（重构）、`docs/`（文档）。
- **提交信息**：遵循 **Conventional Commits**，格式 `feat(auth): 新增用户登录功能`。
- **PR要求**：标题格式 `"[类型] 简短描述"`，需通过 lint、类型校验、全量测试，且至少 1 人审核通过方可合并。

### 4.3 测试要求
- **框架**：Vitest + React Testing Library。
- **覆盖范围**：工具函数 100% 单元测试，组件测试覆盖核心交互流程（点击/输入/渲染）。
- **执行与目标**：命令 `pnpm test`，代码覆盖率 ≥ 80%。

---

## 五、确认与执行

### 5.1 不需要确认
- 不涉及改动文件、执行命令、提交更改的操作，如仅讨论、方案编写、生成代码片段等。

### 5.2 需要确认
- 涉及更改文件、执行命令、提交改动的操作，如改动依赖、文件内容更新等。

---

## 六、子目录中的 `AGENTS.md` 文件要求

在每个项目的子目录下，必须包含一个 **`AGENTS.md`** 文件，确保每个模块都详细记录其功能、调用关系和需求变更。具体内容如下：

### 6.1 模块简介
- **目录功能**：简要描述该目录下代码的功能和作用，解释该目录处理的业务模块是什么，如“用户认证模块”或“数据处理模块”。
- **模块责任**：该目录主要负责的任务和涉及的业务领域。

### 6.2 代码功能与模块划分
- **功能概述**：列出该目录下的主要功能，简要解释每个功能的目的和使用场景。
- 例如：`auth.ts`：负责用户的登录和注册流程
- `database.ts`：处理数据库连接与查询
- **子模块划分**：如果目录中的功能较多，可以进一步将其按子模块划分。

### 6.3 代码调用方式
- **功能调用**：描述该目录内各功能模块之间的调用关系。
- 例如：`auth.ts` 被 `userController.ts` 调用进行用户认证。
- `database.ts` 提供数据库连接方法，供 `auth.ts` 和 `userController.ts` 使用。
- **外部调用**：如果该目录的功能被其他目录或模块调用，也需要在此处详细列出。

### 6.4 需求与修改记录
每次修改该子目录下的代码时，更新以下内容：
- **需求描述**：记录需求的变更，描述新增功能或修改的内容。
- **代码修改方向**：简要描述代码修改的方向、目的和解决的问题。
- **变更背景**：如果适用，可以简要说明变更的背景（如客户反馈、技术债务、性能优化等）。

### 6.5 依赖与冲突说明
- **外部依赖**：列出该目录依赖的其他模块、工具或库。
- 例如：“依赖 `axios` 进行网络请求”。
- **已知冲突**：如果在该目录的开发过程中有已知的冲突或技术障碍，记录在这里，以供后续解决。

---

## 七、如何在每次代码修改后自动更新 `AGENTS.md`

每次修改该子目录下的代码时，按照以下步骤更新 **`AGENTS.md`** 文件：

### 7.1 修改代码时自动记录需求与变更
1. **需求确认**：在进行代码修改前，明确需求，补充缺失的场景和约束，修正歧义，确保需求描述清晰。
2. **代码修改后更新记录**：记录代码修改方向、需求变更、代码调用关系等信息，确保这些更新及时反映到 **`AGENTS.md`** 文件中。
3. **检查更新**：在提交代码前，检查该目录下的 **`AGENTS.md`** 文件，确保更新内容已经反映。

### 7.2 自动化工具支持
可以通过 Git hook（如 pre-commit）或 CI/CD 流水线在提交前提醒开发人员更新 **`AGENTS.md`** 文件。通过自动化脚本，确保每次修改后 **`AGENTS.md`** 都能被及时更新。

---

### **总结**

- 在每个子目录下创建 **`AGENTS.md`** 文件，记录该目录的功能、代码调用关系、需求变更与修改方向。
- 每次代码修改后，确保将修改内容记录到对应的 **`AGENTS.md`** 文件中。
- 可以使用自动化工具来确保 **`AGENTS.md`** 文件的更新与维护。
